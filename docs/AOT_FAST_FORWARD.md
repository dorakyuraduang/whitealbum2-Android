# 静态重编译版快进优化

2026-11-08，0.2.48 引入、0.2.49 补充。仅使用已有生成 C++、CFG 和自有内存测试；没有读取或执行原 EXE，没有启动游戏、模拟器、图形设备或读取屏幕。

没有发现宿主另加的“最多 2 倍/4 倍”等固定快进倍速。`recompiled/process.cpp` 进入 `Program::invoke_unmetered`；原生实验引擎的每帧 2 ms/256 tick 预算不属于这条 AOT 执行路径。

保留代码仍有以下节奏控制：

- 缓存主循环 `0x4337c6` 向更新函数传入 60。更新函数 `0x418d90` 维护下一次更新时刻；`0x418f22` 检查快进条件并存在提前更新分支，因此不能简单称为“快进固定锁 60”。
- 主消息/设备循环中仍有源程序的 `Sleep(2)`。0.2.48 仅在有效剧情快进时省去返回位置为 `0x4337d8` 的主循环空闲等待，继续轮询输入、音频和工作线程，并向操作系统让步。设备恢复循环、工作线程的 Sleep、对象等待和宿主内部等待不变。
- `platform/render/source_graphics.cpp` 通常按源程序的 presentation interval 请求垂直同步；IMMEDIATE 对应 0，其他请求对应 1。0.2.48 在有效剧情快进时请求关闭垂直同步，并合并过密的最终窗口提交；普通播放、菜单、取消快进和影片恢复原同步请求。驱动可能拒绝关闭同步；每次状态转换只发一次请求，并记录实际结果。
- `0x40ad10` 的快进判定及 `0x40af20` 的等待逻辑仍检查输入、既读/模式和取消条件。影片、选择项、语音/资源等待也不能按普通文字批量跳过。

快进判断放在共享 AOT 运行时，调度与绘制适配器只接受通用策略回调。`recompiled/fast_forward.hpp` 只读检查缓存 `0x40ad10/0x405200` 的按键、锁存、既读和取消条件，以及当前/最近更新的剧情状态 3；不从设备回调重入游戏函数，不更改源程序的快进开关。陌生或溢出的既读索引、不可读状态、窗口切换和非剧情状态均不启用优化。

0.2.49 进一步排除故事状态内部的存档/读档界面：缓存 `0x41a783/0x41ef89` 将 `0xa39208` 设为 6/7。即使先前快进按键或锁存仍然存在，这两个界面也保留普通空闲等待与同步设置。测试检查保留快进标记进入两界面时不触发等待缩短；剧情中的快进优化仍保留。

屏幕提交至多每 8,333,334 ns 一次，约 120 Hz；这只控制最终窗口的 blit/swap，**不限制快进逻辑更新次数**。每次源 Present 仍先刷新全部排队绘制、更新离屏/后备缓冲、校验矩形并检查 GL 错误。读取画面、增量绘制、资源生命周期、影片时间线和音频时钟继续有效。影片结束恢复游戏画面时强制提交一帧。

内存测试将只读快进判断与同一份未改动的静态函数比较，覆盖两种内存模式、既读/未读、两种输入、模式/取消和覆盖标记；另检查准确的 Sleep 调用位置、工作线程、对象等待、不缩放的时钟及受控时间下的提交/同步恢复。生成的游戏函数保持不变。Windows x64 与 Android ARM64 编译同一份策略和适配器。

这两处能去掉无谓等待，但不消除脚本、资源解码、粒子和离屏绘制的实际耗时。没有运行整段游戏或手机实测，不能给出提速倍数、达到原版几成或手机帧率。当前退出/错误报告中的 `scheduler.accelerated_idle_calls`、`accelerated_idle_requested_ms` 和 `direct3d9.coalesced_fast_forward_presents` 可区分实际命中量；它们不是实测提速倍数。

2026-11-09，`0.2.55` 优化快进中的重复资源读取。此前图片解压缓存仅在第二次使用后保留，第三次才命中，且大于 4 MiB 的图片一直不能进入缓存。现在首次解压耗时至少 500,000 ns 的压缩图片可直接保留，较便宜的图片仍需重复后保留；单项允许至 8 MiB，总保留上限仍是 8 MiB/32 项。命中后仍创建新的游戏缓冲、复制不可变字节并恢复完整最终字典；归档大小/时间变化和实际依赖的 18 个字典尾字节变化都不能错误复用。持续读新图片、超过上限或已淘汰的资源仍需正常读取与解压，首次保留还会多一次有界复制，不能据此宣称所有加载都更快。

`tests/resource_reuse.cpp` 使用自建 5 MiB 图片与字典依赖流，执行分页/连续两种内存模式下的 18 次完整资源 ABI 加载，核对全部输出、最终字典、调试结果、新分配及归档失效，确认命中时不再读取图片内容。独立策略检查覆盖解压阈值、便宜/未压缩数据、空/超限输入、8 MiB 总量、32 项淘汰和已返回对象的寿命；`tests/resource_loading.cpp` 保留通用资源的 64 个完整输出、22 个失败、8 个别名和 2 个映射变化检查。这些是无游戏、无画面的组件验证，不是安卓快进倍数或首次加载时间测试。

私有阶段报告现在也响应资源活动，继续限制为每 500 ms 至多一次、每次运行最多 64 次，不依赖存档读取才能更新。`native_resources.image_payload_reads/bytes` 记录实际完成的图片内容读取；`image_decoded_cache_cold_captures` 记录首次保留命中政策的数量。`timing.image_cache_store` 单独计入保留成本，通用加载增加 `resource_load/read/validate/decode/allocate_and_copy` 分段；分段含嵌套计时，不能简单相加当作总耗时。资源计数不包含屏幕、所选目录 URI 或文件内容。Windows x64 与 Android ARM64 使用同一缓存和加载实现，原 PAK 保持外置，目录名不限。

用户实测 `0.2.55` 后仍反馈快进慢。本轮读取到的阶段快照含 245 次图片加载、69 次缓存命中、176 次内容读取（85,700,428 字节），图片加载累计 621.518 ms，30 次通用资源加载累计 138.094 ms；缓存保留复制累计 42.704 ms。`main_sleep_wall_ns` 为 13.484 s，但它包含 Sleep 内执行的线程/设备轮询，并非纯系统休眠，而且阶段记录混合启动、菜单、普通播放与快进，不能据此计算快进占比或直接断言等待是唯一瓶颈。报告不完整的旧退出记录属于 `0.2.51`，没有将其绘制数据用于当前性能结论。缓存确已生效，但这次实际反馈不能支持“快进已修好”。

`0.2.56` 合并共享 SDL 窗口适配器在 1 ms 内的非阻塞事件泵调用。此前光标、按键和消息 API 每次都进入 SDL 轮询及原生控件队列；现在重复查询继续读取已维护的输入状态，实际事件留在原队列中，下一次泵保留各事件顺序与点击位置。按键低位仍按每次查询消费；正超时的阻塞请求、窗口创建/销毁及回退的时钟绕过合并。它最多增加 1 ms 的非阻塞输入采集间隔，不跳过剧情、图片或音频处理。

为了继续定位，阶段记录加入不含逐帧数组的 `frame_work` 绘制/交换汇总、`host_event_pump` 次数和 `static_cpu_work` 抽样；函数采样包含直接子调用，估算项不能直接相加。`scheduler.sleep_poll_wall_ns` 与 `sleep_os_wait_ns` 区分 Sleep 内工作和系统条件等待，源程序期限不变。资源独自变化时最低 2 s 才写一次，文件访问变化仍至少间隔 500 ms，总尝试次数仍为 64。长 Android 日志按最多 640 字节且不切断 UTF-8 的小段传输，收集器仅发布完整 JSON；旧版截断行会被明确标为不完整，而不会把早期的零计数当作当前结果。`tests/host_progress.cpp` 的受控时间验证包含阻塞绕过、边界、时钟回退、计数、分段重组与精确汇总，Python 夹具检查完整/缺段/乱序/重复/截断及版本隔离；均不启动游戏或 SDL 设备。这些检查仍不是整机提速倍数验证。

用户实测 0.2.56 仍反馈慢。该次阶段记录的事件泵已将 139,170 次查询合并为 3,178 次设备轮询；快进中的一段约 7.7 s 窗口，函数执行边界累计约 6.8 s。随后只附加到用户手动运行的本游戏进程，以 99 Hz 采集约 20 s 用户态 CPU 栈，共 1,806 样本、零丢样，没有启动游戏或读取屏幕。两个没有互相调用的图片处理函数 `0x438820` 和 `0x438a00` 的包含子调用样本分别约占 55.1% 和 28.8%；LZSS 自身约 0.8%。这说明本轮真正占 CPU 的是读取后的灰度/饱和度像素处理，不能把“加载时卡住”全归因于存储吞吐。栈采样的嵌套项不可重复相加；该占比描述这段实测，不代表所有场景。

0.2.57 为这两个函数的六个像素循环添加原生批处理。`engine/image_chroma.*` 只接收普通字节缓冲和两行当前查找表；按缓存源代码的整数权重、加法截断和 RGB/BGR 顺序计算，不用近似颜色公式替换原表。`recompiled/image_chroma.*` 验证完整可读写范围、表/栈别名、计数和地址边界，恢复循环出口的整数寄存器、标志与栈计数；分页模式按单个物理页批量，只有跨页像素使用逐字节检查。Alpha/填充保持原值，权限故障、可执行目标、未知参数和重叠布局保留原有路径。它不增加全图暂存、资源解压落盘或缓存预算。

原有 42 个缓存生成输入继续与历史收据逐字节匹配。一个公开的准备脚本从它们产生两份两平台共用的派生单元，只插入六处入口并调整 include；CMake 和验证报告记录输入、配方和产物的散列。原静态循环也保留在同一函数，计量版本不进入新路径。`tests/image_chroma.cpp` 对照从未改动输入提取的完整参考函数：756 组整函数的 CPU/标志/浮点字节/栈/图片结果、36 组原计量执行停在循环出口的中间状态、90 组边界/拒绝案例（含 42 个精确故障）及 6 组末端部分页检查通过。连续基址和分页两条路径都实际执行；测试原色表、不同偏移、负/越界计数、Alpha、表重叠和部分写入。

同机五轮交错处理每组 262,144 像素，参考函数保留原 `-Oz` 优化设置，普通 C++ 像素核心使用 `-O3`。分页模式三类中位数约 4.87/11.65/10.90 ms → 0.23/0.27/0.25 ms，连续基址约 4.69/11.25/10.48 ms → 0.20/0.26/0.24 ms，组件配对约 21–44 倍。它们不是 Android 整机、整段快进或帧率倍数；完整性能仍需新版在原测试场景中的反馈。只读计数中的 `native_image_chroma` 用于确认实际接纳量。

用户覆盖安装 0.2.57 后在测试场景反馈“明显变快”。当时只读阶段记录仍停在标题阶段，尚不能据其零计数声称得到剧情中的实际接纳次数。诊断触发已补入图片处理完成数，使复用源图、没有新读包时的颜色处理也能刷新记录。此反馈支持本轮有实际改善，但没有据此宣称整机达到 21–44 倍或固定帧率。
