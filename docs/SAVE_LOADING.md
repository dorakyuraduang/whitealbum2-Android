# 目录存档读取检查

2026-11-08，更新至 0.2.50-shared-aot。针对用户反馈读档等待很久，检查已有 C++、Java、生成静态代码及缓存 CFG。没有打开原 EXE、运行游戏、操作菜单或访问屏幕；没有把组件查询量当作实机读档秒数。

发现并修正的额外开销：

- 共享文件 API 的 CreateFile 先查询是否存在，再解析共享锁用的路径，最后打开文件。原目录别名适配器在这三步中反复解析同一文件，根目录已有文件会触发四次底层元数据查询。现在 `MutableFiles::OpenPlan` 在一次 API 操作内保留已解析的元数据、别名与打开动作；共享锁检查仍在创建或截断文件之前。下一次 API 操作重新查询，不保留跨操作的文件缓存。
- 安卓 `GameDocuments.compatibleMetadata` 列目录时，先取目录列表，再为每个条目调用 child；child 又重取整个目录。现在同次操作的 `DocumentDirectory` 为每个目录建立一次索引，目录遍历和查询复用它。发布、恢复、重命名和删除同步更新此索引。
- `GameDocuments` 的各入口清空索引并串行执行，包括启动页复用同一对象的情况。新操作立即看见外部替换或新增文件；没有依赖超时失效，也没有缓存 PAK 或存档内容。
- 快进策略原先只检查外层故事状态，存读档界面也处于该状态。现在显式排除缓存界面状态 6/7，防止遗留快进标记令文件界面进入加速换帧路径。必要的资源/线程等待不被省略。

检查使用自建文件与内存提供者：共享 C++ 文件 API 的 32 次根目录存档打开对应 32 次底层元数据查询；另外覆盖缺失文件、旧 PC 子目录后备、路径别名、截断前共享锁、下一次操作可见的文件修改/删除，以及原有配置与测试模式隔离。Java 生产索引的 400 次同目录查询只读取一份目录列表，并覆盖下一操作刷新、写入索引更新、大小与重名保护。两平台仍编译同一份游戏静态代码与共同文件适配逻辑。

这些检查能证明重复查询已减少，不能证明用户报告的全部等待都由它引起。点击读档确认后仍需解析存档并恢复场景、图片与声音；文档提供者延迟及完整场景恢复耗时尚未在用户设备上定位或测量。

0.2.49 后用户仍反馈安卓十多秒等待，因此 0.2.50 继续减少整组槽位检查的访问次数。`recompiled/save_read_scope.hpp` 仅对主线程、已知只读文件帮助函数以及源程序的存读档界面状态 6/7 启用共享目录清单。缓存 CFG 的 `0x418f8a` 在每次更新后增加 `0xa3a130`；这个累计计数器区别于每秒清零的 FPS 计数器。清单按该更新和界面状态划分，最长保留 250 ms，写入、删除、移动和替换操作使其失效。有打开的写句柄、其他调用位置或工作线程时保留逐操作检查。后备 PC 目录仅查询一次；不可列目录的提供者退回原查询路径。

存档数据不缓存，文件描述符始终重新打开。独立测试调用同一份未修改的静态 `0x4234c0 -> 0x44c4c0 -> CreateFile/ReadFile` 路径，对自建的 100 个槽位、两个有效文件作比较：原路径 198 次文件元数据查询，共享清单后为一次目录列举，两边均打开和读取两份文件。两种内存模式合计 432 次静态读取调用，另覆盖新内容、下一帧、写入后更新、旧目录后备、最长保留期限、线程/写句柄排除与不可列目录的回退。此结果不代表原游戏每次必然扫描 100 个槽位，也不是手机上的倍数或耗时测量。

运行退出报告新增 `selected_directory_io`，区分目录查询、文件元数据、描述符打开次数与纳秒耗时；`file_io` 记录 ReadFile/WriteFile 的次数、字节数、总/最长耗时（包含缓冲分配和桥接复制）。启动页“复制上次运行诊断”读取正常退出后保存在应用私有目录的 `wa2-runtime.json`，只复制版本、错误和 I/O/解码/调度计数摘要。它不读取画面、不复制存档或资源内容，也不在游戏每帧写文件。

同版取消了资源目录名称和提供者名称白名单。用户通过系统选择器授权哪个资源目录，就使用哪个；目录可以有任意名称。资源布局、IC 子目录、持久读写授权及可定位文件描述符的要求仍适用。

## 0.2.51：配置批量读取和无线设备检查

2026-11-09 继续检查发现，`GetPrivateProfileInt/String/Struct` 每读一项都会重新打开、读取并解析整个 INI。私有目录的文件打开很便宜，但授权目录每次都经过 JNI、文档提供者查询和文件描述符打开。只优化存档槽位清单不能消除这些配置访问。

共享 C++ 现在通过 `ProfileReader` 为已知静态调用、主线程和同一累计更新计数保留解析结果。最多保留四份、不超过 256 KiB 的配置，最长 250 ms；下一次更新、存储命名空间切换、明确刷新和任何本应用写入都会使旧结果失效。有打开的写句柄、工作线程、普通 API 调用时继续新读；异常不缓存。配置写入仍立即发布到所选目录，没有私有文件镜像或延迟落盘。外部修改最迟在下一更新或期限到达后重新读取。

内存检查运行与交付版本相同、未改动的静态 `0x44d4e0` 配置读取包装函数。两种内存模式合计 624 次调用；100 项配置的底层打开由 100 次减为一次，缺失 INI 的默认值也只检查一次。另覆盖文件写入、直接配置写入、显式刷新、下一更新、超时、工作线程、写句柄、命名空间替换及失败后重试。`profile_io` 运行摘要记录逻辑读取、快照命中、物理读取次数和耗时；写入从不延迟。

`tests/android-device/StorageProbe.java` 和 `native_storage_probe.cpp` 提供独立的无 Activity 仪器测试，构建命令见 [设备文件测试](../tests/android-device/README.md)。它使用相同签名进入应用 UID，读取持久目录授权和已有诊断，调用真实 `GameDocuments` 与共享静态文件函数。它不启动游戏入口、不创建窗口或音频设备、不读屏幕；临时对比文件仅位于应用缓存目录并在测试后删除。若目录中有待恢复的发布临时文件，测试会先拒绝执行。测试 APK 不包含 PAK，也不随正式 APK 分发。

用户授权无线调试后，在 Android 16 / ARM64 手机上完成以下检查；均在后台、没有外部写入时串行运行。手机安装的是 0.2.50，保留的上次游戏报告仍为 0.2.49，不能将该旧报告视作本次完整读档记录。下表使用独立探针编译的新共同核心，Java 目录适配器来自手机安装包：

| 检查 | 基线 | 批量读取 | 实际访问变化 |
| --- | --- | --- | --- |
| 同一份现有 INI，10 次静态包装调用 | 2264 ms | 258 ms | 成功打开 10 → 1，返回序列相同 |
| 10 个存档槽位，其中 1 个有效 | 1463 ms | 111 ms | 逐文件元数据 20 → 0，改为 2 份目录清单；两边均重新打开、读取同一份 65624 字节头部 |

第一项验证 0.2.51 的新配置优化。第二项对比关闭/开启 **已有 0.2.50 清单优化**，不是宣称 0.2.51 又让存档整体快了 13 倍。提供者时延有明显波动，这些是单轮组件数据；源码更新计数在每组测试内固定，没有把多次游戏画面更新混为一次。

另外，同一份 557 字节配置的 20 次普通 Java 读取，私有缓存临时文件合计 0.508 ms，授权目录合计 1978 ms。后者目录查询约 934 ms、打开约 1041 ms，真正读出数据约 1 ms。可确认本机授权目录的重复查询/打开开销很大，不能因此把文件夹名称、手机存储吞吐或 PAK 解压认定为本次等待的唯一原因。尚未操作游戏菜单或测量完整恢复剧情所需时间。保留设备报告在忽略的本机日志目录，不将存档内容、授权 URI、设备连接地址或诊断原件推送公开仓库。

## 0.2.52：根据实际游戏运行报告修正准入条件

用户手动在 0.2.51 读档并正常退出后，无线探针取回了对应版本的报告。50 次配置读取命中 48 次快照，只有两次物理读取、合计 42 ms；但存档清单构建/命中均为零，441 次元数据查询用了 6973 ms，77 次描述符打开用了 2586 ms。约 9.77 MB 的 ReadFile 合计只用 22.9 ms。报告覆盖启动到退出，并非单独计时的读档区间，但它确认真实路径没有进入清单优化，之前的组件测试不足以证明该路径生效。

0.2.52 保留主线程、已知只读帮助函数及写句柄排除条件，去掉剧情子状态 6/7 的准入限制。标题读档等调用也可以在同一源更新中共享元数据；状态仍是快照键的一部分，所以切换状态会刷新。存档内容与文件描述符继续新读，写入立即使清单失效。新增标题状态的静态读取、状态切换及普通 API 新鲜度检查。运行报告的 `save_read_scope` 最多记录 32 组线程、返回地址、状态和写句柄数，用来识别实际路径的拒绝原因；不记录文件内容或画面。修正后的整次手机运行仍需通过用户操作收集报告，不能套用前面的组件倍数。
