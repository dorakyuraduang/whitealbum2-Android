# 目录存档读取检查

2026-11-08，更新至 0.2.50-shared-aot。针对用户反馈读档等待很久，检查已有 C++、Java、生成静态代码及缓存 CFG。没有打开原 EXE、运行游戏、操作菜单或访问屏幕；没有把组件查询量当作实机读档秒数。

发现并修正的额外开销：

- 共享文件 API 的 CreateFile 先查询是否存在，再解析共享锁用的路径，最后打开文件。原目录别名适配器在这三步中反复解析同一文件，根目录已有文件会触发四次底层元数据查询。现在 `MutableFiles::OpenPlan` 在一次 API 操作内保留已解析的元数据、别名与打开动作；共享锁检查仍在创建或截断文件之前。下一次 API 操作重新查询，不保留跨操作的文件缓存。
- 安卓 `GameDocuments.compatibleMetadata` 列目录时，先取目录列表，再为每个条目调用 child；child 又重取整个目录。现在同次操作的 `DocumentDirectory` 为每个目录建立一次索引，目录遍历和查询复用它。发布、恢复、重命名和删除同步更新此索引。
- `GameDocuments` 的各入口清空索引并串行执行，包括启动页复用同一对象的情况。新操作立即看见外部替换或新增文件；没有依赖超时失效，也没有缓存 PAK 或存档内容。
- 快进策略原先只检查外层故事状态，存读档界面也处于该状态。现在显式排除缓存界面状态 6/7，防止遗留快进标记令文件界面进入加速换帧路径。必要的资源/线程等待不被省略。

检查使用自建文件与内存提供者：共享 C++ 文件 API 的 32 次根目录存档打开对应 32 次底层元数据查询；另外覆盖缺失文件、旧 PC 子目录后备、路径别名、截断前共享锁、下一次操作可见的文件修改/删除，以及原有配置与测试模式隔离。Java 生产索引的 400 次同目录查询只读取一份目录列表，并覆盖下一操作刷新、写入索引更新、大小与重名保护。两平台仍编译同一份游戏静态代码与共同文件适配逻辑。

这些检查能证明重复查询已减少，不能证明用户报告的全部等待都由它引起。点击读档确认后仍需解析存档并恢复场景、图片与声音；文档提供者延迟及完整场景恢复耗时尚未在用户设备上定位或测量。

0.2.49 后用户仍反馈安卓十多秒等待，因此 0.2.50 继续减少整组槽位检查的访问次数。`recompiled/save_read_scope.hpp` 仅对主线程、已知只读文件帮助函数以及源程序的存读档界面状态 6/7 启用共享目录清单。缓存 CFG 的 `0x418f8a` 在每次更新后增加 `0xa3a130`；这个累计计数器区别于每秒清零的 FPS 计数器。清单按该更新和界面状态划分，最长保留 250 ms，写入、删除、移动和替换操作使其失效。有打开的写句柄、其他调用位置或工作线程时保留逐操作检查。后备 PC 目录仅查询一次；不可列目录的提供者退回原查询路径。

存档数据不缓存，文件描述符始终重新打开。独立测试调用同一份未修改的静态 `0x4234c0 -> 0x44c4c0 -> CreateFile/ReadFile` 路径，对自建的 100 个槽位、两个有效文件作比较：原路径 198 次文件元数据查询，共享清单后为一次目录列举，两边均打开和读取两份文件。两种内存模式合计 432 次静态读取调用，另覆盖新内容、下一帧、写入后更新、旧目录后备、最长保留期限、线程/写句柄排除与不可列目录的回退。此结果不代表原游戏每次必然扫描 100 个槽位，也不是手机上的倍数或耗时测量。

运行退出报告新增 `selected_directory_io`，区分目录查询、文件元数据、描述符打开次数与纳秒耗时；`file_io` 记录 ReadFile/WriteFile 的次数、字节数、总/最长耗时（包含缓冲分配和桥接复制）。启动页“复制上次运行诊断”读取正常退出后保存在应用私有目录的 `wa2-runtime.json`，只复制版本、错误和 I/O/解码/调度计数摘要。它不读取画面、不复制存档或资源内容，也不在游戏每帧写文件。

同版取消了资源目录名称和提供者名称白名单。用户通过系统选择器授权哪个资源目录，就使用哪个；目录可以有任意名称。资源布局、IC 子目录、持久读写授权及可定位文件描述符的要求仍适用。
