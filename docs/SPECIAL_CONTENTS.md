## Android 采用一个 APK

沿用现有启动页的正篇和 **Special Contents** 入口。两者共用同一套窗口、
输入、图形、音频、文件访问和设备适配源码。两套原始程序分别生成静态 C++；
每套生成结果同时供 Windows x64 和 Android ARM64 编译，不按平台另写游戏逻辑。

Special 的原程序地址、CRT、资源表和部分 UI 与正篇不同，不能直接使用正篇地址补丁。
它在非导出的 `SpecialContentsActivity`、`:special` 进程中加载 `libwa2_special.so`。
正篇继续加载原来的运行库。进程隔离使重叠的源程序地址、SDL/JNI 会话、资源选择
和配置互不覆盖，也无需维护第二个应用的安装、签名和启动接口。

合包核验会逐字节保留已验证正篇 APK 的三个运行库和许可证条目，只新增 Special
运行库及对应入口。当前合包版本为 `0.2.115-special-aot`；正篇运行库的诊断版本仍是
`0.2.108-shared-aot`。安装使用 `adb install -r`，核对版本、UID、首次安装时间和
已安装 APK 的 SHA-256，不卸载、不清数据、不启动应用。

## 资源和存档

点击启动页的 **Special Contents**，选择该版本自己的原资源文件夹并授予持久读写权限。
保留它自己的 PAK 文件名和内容，不与正篇的同名 PAK 混放，也不需要解包。
文件夹名称不限；原始 PAK 不进入 APK。Special 的目录授权不会改写正篇的目录设置。

Special 存档和 INI 配置位于：

```text
<Special 资源目录>/Documents/Leaf/WHITE ALBUM2 Special Contents/
```

源程序的根目录存档/配置别名也映射到这里。正篇 IC/CC 进度目录在 Special 中仅可读；
写入、删除和移动到正篇存档目录会被拒绝。不会自动复制或合并现有存档。
当前没有为 Special 应用正篇的语言替换、附加字幕、全部解锁或固定地址加速补丁。

## 复现

在已有工具依赖的 Windows 工作区，先构建 `build/special-toolchain/winrecomp.exe`，
然后执行以下步骤。编译器与测试子进程必须隐藏、低于正常优先级、每次一个构建任务。

```powershell
python scripts/prepare_special_contents.py --exe 'D:\WHITE ALBUM2 Special Contents\WA2_Special_cn.exe'
python scripts/verify_special_contents.py
python scripts/package_launcher.py --integrated --with-special
```

首次准备检查授权和 SHA，进行静态 CFG/回调发现并保存初始内存。
后续准备复用核验过的缓存，不再读取输入 EXE。原始程序始终不执行。
验证器先用 `scripts/audit_special_callbacks.py` 核验缓存中的数据回调引用，
生成同一套公共 AOT，依次构建两种架构，运行有限的 Windows 内存检查，
比较实际编译的 Special 源文件清单与哈希，并核验 ARM64 ELF 的 16 KiB 装载对齐。
合包必须有当前源码绑定的验证记录，完成签名/内容核验后自动尝试在已授权手机原位安装。
设备不可用时明确记录安装待完成。

本地产物和记录：

- `out/android/WA2-arm64-0.2.113-special-aot.apk`
- `out/special-contents/WA2_Special_SDL2_x64.exe`（使用 `--root <Special 资源目录>`）
- `logs/special-aot-verification.json`
- `logs/special-android-installed.json`

## 0.2.110：字符串操作的预算模式

用户报告 `execution budget exhausted at guest address 4691986`。
该地址为缓存 CFG 中的 `0x479812`，是一条复制 136 个 DWORD 的 `REP MOVSD`。
Special 生成器此前保留了原始指令 oracle 的默认诊断计数参数，而普通静态函数
传入的预算槽为零，导致正常内存拷贝在第一个元素前错误停止。

生成器现在为全部 186 处字符串操作显式传递外围函数的 `Metered` 模式，使用现有
公共 `wr::string_op<Metered>` 语义。没有改变全局预算、内存检查或诊断模式的上限。
Windows 和 Android 编译同一份修正后的生成源码。

有限回归直接恢复到报错指令，使用构造内存及未映射栈，在下一条 PUSH 停止，
不会执行其后的游戏调用。覆盖零次/136 次、正向/反向和跨页拷贝，读取故障前的
两元素完成前缀，以及诊断模式预算耗尽的精确前缀。修复前已复现相同地址和错误；
修复后的六项检查必须通过，打包器才接受新的源码绑定验证记录。
本次 Windows/ARM64 同源重编译及六项回归已通过，`0.2.110-special-aot`（113）
已原位安装到授权手机，UID、首次安装时间和应用数据保留，安装包哈希核验一致。
手机上的再次启动仍由用户控制，整部运行与性能验证继续待完成。

## 0.2.112：CRT 跳转表与启动前的内存工作

手机应用自己的错误日志确认 `4673248`（`0x474ee0`）停止原因为
`missing static function or host service`。它是 `0x474e20` CRT 拷贝函数的
对齐分支，由代码区内部的跳转表引用。0.2.111 补全的是 `.rdata` / `.data`
中的回调表，没有继续采用独立分析记录中的 computed-jump 目标。这是上一次
补全覆盖范围的遗漏，不能把之前的组件检查解释为全部间接目标已经覆盖。

核验现在还从已到达的跳转指令读取独立静态分析的目标，核对源指令字节和
目标指令边界，再递归生成共同 CFG/C++。本次补全两份 CRT 拷贝函数的
26 个分支入口，增加 190 个指令位置。表数据仍是数据，未知的动态目标仍报错。

用户确认黑屏发生在点击 Special 后、主菜单出现前。当前手机日志只提供了
Special 的上述错误，没有可用于归因的 Special 启动耗时记录；同一应用 UID
中的正篇计数不能拿来证明 Special 的耗时或改进幅度。
代码核查发现 Special 的 REP 拷贝/填充此前逐元素调用受检内存，而正篇已使用
公共 `wr::aot_string_op<Metered>` 批量实现。Special 现在在所有平台采用同一
公共实现，符合条件的 MOVS/STOS 先验证整个范围，再完成批量操作；重叠、
权限不足、未映射、地址回绕、分段等不符合条件的情况保留原来的逐元素语义和
精确故障前缀。诊断模式继续逐元素计数，不放宽预算。

有限内存回归实际执行两份完整 CRT 拷贝函数，覆盖全部四字节对齐组合、
短长度、跨页、大块数据、双向重叠、同址拷贝以及 SSE2 选择路径，检查结果、
返回值、栈、非易失寄存器和方向标志。此前 REP、初始化回调与代码边界检查继续执行。

Special 还接入公共的低频静态函数采样，在自己的保存目录适配器记录元数据、
枚举、打开和目录操作耗时。启动阶段分别记录运行库准备、保存目录、资源挂载、
初始内存装载和源程序启动的时间边界；失败时也会发出最终 CPU/文件计数。
Android 使用现有分块计数输出，避免长 JSON 被系统日志截断。可按以下方式只读收集：

```powershell

```

这些修正不构成手机加载时间改善的实测证据。新版的主菜单前等待与完整运行结果，
仍需用户控制的手机启动以及相同场景、设置下的计数对比，不运行 PC 游戏或模拟器。

## 0.2.113：扩展精度运算与已定位的解压热点

授权手机的应用日志确认 `4642967`（`0x46d897`）在 `FYL2X` 处停止，
错误为 `x87 transcendental result/status contract is not established`。
它属于一个同时计算对数和正余弦表的初始化函数。这里只补入口不能解决问题，
也不能删除检查后使用宿主默认精度的近似数学函数。

公共后端接入固定版本的 SoftFloat/Bochs 纯算术源码，实现 80 位扩展精度的
`FYL2X`、`FYL2XP1`、`F2XM1`、`FPATAN`、`FSIN`、`FCOS`、`FPTAN`。
没有编译 CPU、设备模型、指令解码器或模拟器，也不在生产库中执行宿主 x87 指令。
第三方来源、原始文件哈希、许可证和重建入口见 `third_party/x87_math`。
Android 包和 Windows 产物附带许可证通知，正篇已验证运行库按原有合包规则保留。

`scripts/verify_x87_transcendental.py` 在隐藏、低优先级、单任务的有限内存程序中，
以本机指令作为独立对照，检查 107,520 组输入的状态字、有效栈寄存器和控制字，
并核对序列化及寄存器文件两种表示。覆盖三种精度控制、四种舍入、扩展指数边界、
非规格数、NaN、无穷、无效编码和栈占用。修正三角函数越界时 C1 的清理、
无效编码判定以及 FPTAN 栈异常的优先级和双 NaN 响应后，全部对照通过。
这不是所有位模式或所有 x86 处理器型号的穷举证明。

Special 的 50 处相关位置统一生成软件算术调用；新增实际指令回归从报错地址恢复，
计算两次对数及其后比值，在写入刻意未映射的栈时停止，避免进入随后的游戏调用。
未知入口和未屏蔽浮点异常的可恢复交付仍保持明确失败。

0.2.112 的手机日志记录本轮到报错约 42.05 秒，最近一次呈现计数中的静态函数边界
累计约 36.59 秒，单次最大呈现间隔约 27.65 秒；这些包含性计数不能相加。
静态函数抽样中 `0x438270` 的首个样本约 3.79 秒，经缓存 CFG 确认为资源 LZSS
解压循环。抽样估计不是该函数全部调用的准确总耗时。

输出长度、缓冲区有效且相互不重叠的流，输入和输出分别不超过 64 MiB。
解码结果及字典完成后恢复原循环的计数、参数槽位和指针，继续 `0x4382b0` 的

接纳检查不改变调用状态并继续原流程。没有保留资源载荷缓存，也没有缩短游戏等待。

内存对照检查完整原循环和该路径的返回值、输出、全部 4 KiB 字典、栈和浮点状态，

## 0.2.114：修正 Logo 停滞与音频解码接入

用户反馈 Logo 显示一半停住，声音卡顿或重复。第一次应用计数中，40 次 LZSS
解压全部完成，合计约 0.122 秒；这些计数不支持把停滞归因于解压内核。
在用户手动复现并保持前台后，帧计数停在 57，样本已经过期约 38 秒，游戏线程
约占一个 CPU 核。8 秒、99 Hz 的应用限定采样获得 818 个样本且无丢失，约 96%
的包含调用链位于公共调度器的音频工作线程内，主要经过 `0x458890`、`0x464b20`、

## 0.2.115：缺失文件探测触发的存储异常

用户控制的 0.2.114 运行在约 29.65 秒后报告 `Unknown Special storage path`。
结束计数中公共 Vorbis 已完成 40 次解码、输出 1,821,824 字节，错误和拒绝数均为
零，帧计数为 2,253。该记录确认公共解码路径在运行，不构成同场景 FPS 对比或
整部游戏验证。旧错误未记录被探测的具体文件名。

问题在 Special 的 `MutableFiles::identity()` 实现：公共 `prepare_open()` 在文件
不存在时也会先取得用于共享检查的标识，Delete/Move 在检查权限之前也查询它。
Special 却把未映射的共享标识当成致命错误，导致一次普通的缺失文件探测终止
整个游戏线程。

标识查询现在对未映射名称返回规范化的比较键，不查询底层目录，也不授予文件
访问权限。实际元数据、打开、删除、移动及写入仍受原来的 Special 路径限制。
缺失文件通过 CreateFile 返回错误 2，未允许的创建和修改返回错误 5；正常存档
及其大小写、分隔符别名仍共用同一个共享访问标识。进度记录新增未映射标识
查询次数及最多 256 字节的最近逻辑名称，便于后续定位，不记录资源目录的主机路径。

有限内存回归先在旧实现中复现相同错误，修复后 34 组实际 Win32 API 检查通过，
覆盖 A/W 文件探测、三种创建方式、属性、带活动句柄的删除／移动、存档别名
共享冲突，并核对未映射操作完全没有到达底层文件提供者。既有目录越界及
正篇存档写入隔离检查保留；音频、浮点、CRT、回调及解压检查继续通过。
Windows x64 与 Android ARM64 继续编译相同的生成源码和公共实现。
